# 架构分层说明写法

流程图只回答了「谁在什么时候做了什么」。分层说明回答的是「这张图为什么这样分层、哪一层是瓶颈、边界在哪」。

**核心原则：只讲图上看不出来的信息。** 把箭头复述一遍等于没写。

## 固定四段

### 一、角色层：谁对结果负责

- 列出每个泳道角色的**职责边界**，一句话一个。
- 标出**唯一责任方**：每个关键结果（退款到账、拒收成立）必须只有一个角色负最终责任。
- 标出**无责任方**：流程里出现但不对结果负责的角色（纯通知方），明确写出来。

```text
买家：发起退货、寄回商品，不参与验收判定。
商家：审核申请、确认退款，对「是否同意退货」负最终责任。
平台客服：仅在验收争议时介入，对「争议判责」负最终责任。
仓储系统：执行入库验收，只提供验收结论，不决策退款。
```

### 二、流程层：主干与分支的关系

- 说明主干一共几步、经过几个交接点。
- 说明每条异常分支**从主干哪一步岔出去、回到哪一步或终止**。
- 标出**并行点**（同一时刻多个角色可同时动作）与**同步点**（必须等齐才能继续）。

```text
主干 5 步，3 个跨角色交接点（买家→商家、商家→买家、买家→仓储）。
异常 E1 从「商家审核」岔出，直接终止，不回流主干。
异常 E2 从「入库验收」岔出，回流至平台客服判责，判责后终止或退回买家。
无并行点；「商家审核」与「买家寄回」为串行，不可同时进行。
```

### 三、系统层：哪个系统真正干活

- 区分**人做的动作**与**系统自动做的动作**。
- 标出跨系统调用：谁调谁、靠什么触发（定时任务 / 消息 / 同步接口）。
- 标出**系统边界**：哪些环节需要人工介入，说明为什么不能自动化。

```text
自动动作：48h 超时检测由平台定时任务触发，无需人工。
人工动作：验收判定由仓储人员执行，因需实物核验，不自动化。
跨系统：平台订单系统 → 仓储 WMS，通过退货单号同步触发。
系统边界：退款金额计算在平台侧完成，仓储系统不接触资金。
```

### 四、异常与边界：还差什么

- 列出图上**没有画、但真实存在**的风险点。
- 明确列出「待确认项」，不要把不确定的地方写成确定结论。

```text
未覆盖：买家恶意退货的识别与风控拦截。
未覆盖：退款接口失败后的重试与补偿。
待确认：48h 计时是否含节假日。
待确认：验收不合格时，退回运费由谁承担。
```

## 写作要求

| 要求 | 说明 |
|---|---|
| 短句 | 一句话说一件事，别用长定语 |
| 具体 | 写「48 小时」「退货单号」，不写「一段时间」「相关单据」 |
| 有主语 | 写「平台定时任务触发」，不写「被触发」 |
| 不复述箭头 | 图上已有的连边关系不重复描述 |
| 不编造 | 素材里没有的结论一律进「待确认」 |
| 篇幅 | 四段合计 200–400 字。超过 500 字说明图没画清楚 |

## 交付格式

```markdown
## 架构分层说明

### 角色层
...

### 流程层
...

### 系统层
...

### 异常与边界
...
```

放在 Mermaid 源码同一个 Markdown 文件里，图在前、说明在后。
