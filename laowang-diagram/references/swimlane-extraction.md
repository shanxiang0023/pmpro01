# 从大白话抽取泳道结构

把用户口语化的业务描述，转成「角色 / 主干 / 异常」三份可核验清单。这一步不画图，只出清单。

## 一、抽角色

角色 = **承担动作的主体**，不是部门名，也不是系统模块名。

判断口径：

| 是角色 | 不是角色 |
|---|---|
| 买家、商家、平台客服、仓储系统 | 「交易环节」「售后模块」 |
| 运营、财务、风控 | 「订单中心」（除非它真的独立发消息） |
| 第三方支付、物流承运商 | 「其他」「相关方」 |

规则：

1. 一个角色一个泳道。角色数 > 6 时先问用户能否合并，别直接画成 8 条泳道。
2. 系统类角色照样算泳道（仓储系统、风控引擎、消息网关），因为流程图上它们的动作要可见。
3. 「用户」太泛时拆开：C 端买家、B 端商家、内部运营，三者动作完全不同。

## 二、抽主干

主干 = 从触发到结束的**正常路径**，每条写成 `谁 → 做什么 → 交给谁`。

抽取动作时抓三类动词：

- **提交类**：申请、发起、上传、提单
- **处理类**：审核、验收、复核、计算
- **通知类**：通知、回传、推送、同步

规则：

1. 每个动作必须有明确主语。没有主语的句子（「然后就被拒绝了」）要回问是谁拒绝的。
2. 相邻动作跨了角色，就是一个**交接点**，图上必须显式连边。
3. 主干只留正常路径。任何带「如果」「万一」「超时」的，全部移入异常清单。

## 三、抽异常（最容易被漏掉的一步）

异常 = 让流程偏离正常路径的**触发条件 + 处理方 + 结果**。

按下面四问逐条扫，扫不出来就说明素材还不够：

### 异常四问

| 问题 | 典型分支 | 常见漏项 |
|---|---|---|
| **超时了怎么办？** | 卖家超时未处理 → 系统自动退款；客服超时未响应 → 升级 | 只写了「等待」，没写等不到怎么办 |
| **拒绝了怎么办？** | 验收不合格拒收 → 退回买家；审核驳回 → 重新提交 | 只写了驳回，没写驳回后回到哪一步 |
| **失败了怎么办？** | 支付失败、接口超时、库存扣减失败 | 只画成功回调 |
| **冲突了怎么办？** | 并发重复提交、重复退款、状态被并发修改 | 完全没考虑幂等与并发 |

### 每条异常必须写全三个字段

```text
触发条件：卖家在 48 小时内未处理退货申请
处理方：平台系统
结果：自动发起退款，流程终止，不再进入商家验收环节
```

缺任何一个字段，都要回问用户。**不要用「异常处理」四个字糊过去。**

## 四、追问清单（素材不足时用）

按优先级从高到低问，**一次只问 1–3 个**，不要一次甩十条：

1. 这个流程从哪件事开始触发？到哪一步算彻底结束？
2. 除正常走完之外，最常出岔子的是哪一步？
3. 有没有「等一个人/一个系统处理，但他不处理」的情况？超时后谁来兜底？
4. 有没有驳回、退回、重来的环节？退回后回到哪一步？
5. 图里的系统，是同一套还是跨系统？跨系统的地方谁负责通知谁？
6. 有没有可能同一个人重复操作、或者两个人同时操作同一条数据？

问完仍缺的信息，在交付时明确列出「待确认项」，**不要自行补齐**。

## 五、内部清单模板

抽完后整理成这个结构，作为画图的唯一依据：

```text
流程名：电商退货退款
触发：买家在订单页点击「申请退货」
结束：退款到账 或 拒收后流程关闭

角色：
  L1 买家
  L2 商家
  L3 平台客服
  L4 仓储系统

主干：
  1. 买家 → 提交退货申请 → 商家
  2. 商家 → 审核通过 → 买家
  3. 买家 → 寄回商品 → 仓储系统
  4. 仓储系统 → 入库验收合格 → 商家
  5. 商家 → 确认退款 → 买家（收到退款）

异常：
  E1 触发：商家 48h 未处理
     处理方：平台系统
     结果：自动退款，流程终止
  E2 触发：仓储验收不合格
     处理方：仓储系统 → 平台客服
     结果：拒收退回，客服介入判责
```

清单确认后再进下一步。结构错了，图画得再漂亮也是废的。
