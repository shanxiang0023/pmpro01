# IA Draft — 会员系统前台页面原型

> Phase 0 产出。从 brief 推导，禁止套用固定后台页面清单。

## Brief 摘要

- 原文要点：生成会员系统的前台页面原型。
- 产品类型：C 端 / 用户前台。
- 首批范围：覆盖用户理解会员价值、选择套餐、确认开通、查看会员状态与权益入口。

## 1. 核心实体

| 实体 | 说明 | 来源 |
|------|------|------|
| 会员身份 | 用户当前是否为会员、等级、到期时间 | brief 原文 |
| 会员套餐 | 月卡、季卡、年卡等可购买方案 | 推断·待确认 |
| 会员权益 | 开通后可获得的功能、服务、折扣或内容权限 | 推断·待确认 |
| 开通订单 | 用户选择套餐后的支付确认信息 | 推断·待确认 |
| 用户账户 | 展示头像、昵称、会员状态、订单入口 | 推断·待确认 |

## 2. 角色与目标

| 角色 | 主要目标 | 来源 |
|------|----------|------|
| 普通用户 / 潜在会员 | 快速理解会员值不值得开，并完成开通 | 推断·待确认 |

## 3. 关键任务链

### 任务链 #1

```text
[普通用户] 要判断是否开通会员 → 需要看到核心权益、会员状态、推荐套餐 → 建议页面类型（c_home）
```

### 任务链 #2

```text
[普通用户] 要选择合适套餐 → 需要比较价格、周期、标签、赠品 → 建议页面类型（c_list）
```

### 任务链 #3

```text
[普通用户] 要确认某个权益是否有价值 → 需要查看权益说明、适用范围、使用限制 → 建议页面类型（c_detail）
```

### 任务链 #4

```text
[普通用户] 要完成开通 → 需要确认套餐、优惠、支付金额、协议勾选 → 建议页面类型（c_form）
```

### 任务链 #5

```text
[会员用户] 要查看自己的会员状态 → 需要看到到期时间、可用权益、续费入口、订单记录入口 → 建议页面类型（c_profile）
```

## 4. 页面映射

| page-id | 页面名 | 服务的任务 | 页型 | surface | 优先级 |
|---------|--------|------------|------|---------|--------|
| member-home | 会员首页 | 任务链 #1 | c_home | c_end | P0 |
| plan-select | 套餐选择 | 任务链 #2 | c_list | c_end | P0 |
| benefit-detail | 权益详情 | 任务链 #3 | c_detail | c_end | P1 |
| checkout | 开通确认 | 任务链 #4 | c_form | c_end | P0 |
| my-membership | 我的会员 | 任务链 #5 | c_profile | c_end | P0 |

## 5. Scope Out（明确不做）

- 不做后台会员配置、用户管理、订单审核等内部运营页面。
- 不做完整支付结果页，当前用开通确认页覆盖支付前关键决策。
- 不做登录注册流程，默认用户已登录。
- 不做复杂多级会员成长体系，先用单一会员身份 + 多套餐购买完成 MVP。

## 6. 待确认

- [ ] 会员系统服务对象是内容会员、电商会员、工具会员还是课程会员。
- [ ] 套餐价格、权益名称、优惠规则是否有真实业务口径。
- [ ] 是否需要小程序样式或 App 原生样式。

## 推导依据（必填）

“会员系统前台”最核心的用户行为不是浏览大量页面，而是完成从价值理解到开通支付的转化链路。因此页面数量控制在 5 个：一个承接价值表达的首页，一个承接套餐比较的列表页，一个解释权益的详情页，一个完成支付前确认的表单页，一个承接已开通状态的个人页。未纳入后台配置、登录注册和支付结果页，是因为这些不直接服务首批前台会员转化主链路。
